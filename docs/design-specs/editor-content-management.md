# Design Spec: Управление контентом сайта из браузера

## Problem
Сайт ООО «Волжанин» (React + Vite, GitHub Pages на ветке `gh-pages`, домен ук-волжанин-яр.рф) обновляет контент только разработчик с компьютером. Новость требует файл `src/news/news_N.md` с датой в точном формате внутри текста. Пункт «Информации» требует файл в `public/` и строку в JS-массиве `src/maps/*.js`. Новый раздел требует правки React-кода. Публикация идёт командой `npm run deploy` (в репозитории нет ни одного workflow).

Контент ведёт пожилой человек (редактор). Цель: он делает всё в браузере, нажимает «Сохранить», сайт обновляется сам. Хостить и поддерживать отдельный сервер не нужно.

## Solution Overview
Работа идёт в два этапа. Каждый этап полезен сам по себе.

- **Этап 1. Автодеплой и гайд.** GitHub Actions собирает и публикует сайт при каждом пуше в `dev` и по кнопке «Run workflow». Редактор работает в веб-интерфейсе GitHub по письменной инструкции. Формат контента остаётся прежним.
- **Этап 2. Данные и Pages CMS.** Структура сайта переезжает из JS-кода в файлы данных. Pages CMS даёт редактору формы с полями. Новый раздел «Информации» создаётся кнопкой «Добавить».
- Решение «остановиться на этапе 1 или идти на этап 2» принимается по опыту редактора после этапа 1.

## Scope
- In scope:
  - Workflow сборки и деплоя, переключение Pages на источник «GitHub Actions».
  - Проверка данных в сборке (сломанная сборка оставляет на сайте прошлую версию, GitHub шлёт письмо админам репозитория).
  - Новости: заголовок, дата, текст, картинки.
  - «Информация»: разделы и пункты трёх типов (статья с картинками, PDF, одна картинка).
  - Миграция всех текущих новостей и шести разделов («Общая информация», «Отчётность», «Проверка вентиляции», «Компания», «МКД», «Собрания»).
  - Автосжатие картинок при сборке.
  - Две инструкции для редактора с скриншотами (этап 1 и этап 2).
- Out of scope:
  - Редактирование остальных страниц (Контакты, Услуги, Вакансии, Проекты).
  - Свой бэкенд или собственная админка.
  - Три и более уровня вложенности в «Информации».
  - Дизайн публичного сайта.
  - Продление HTTPS-сертификата домена (см. Open Questions).

## Architecture Sketch
```
Редактор (браузер)
   │  этап 1: github.com → Add file → Commit
   │  этап 2: Pages CMS → форма → «Сохранить»
   ▼
GitHub-репозиторий, ветка dev  (контент = обычные файлы)
   ▼  push
GitHub Actions: проверка данных → сжатие картинок → vite build → deploy-pages
   ▼
GitHub Pages + домен ук-волжанин-яр.рф
```
- Хостинг: GitHub Pages (уже используется). Админка (этап 2): облачный Pages CMS, работает поверх репозитория.
- Данные остаются Markdown/YAML-файлами в репозитории. При отказе Pages CMS редактор возвращается на GitHub web без потери контента.
- Владелец стека: фронтенд на JS/React (Vite). Профиль Flutter/Go не применим.

## Data Model
Названия сущностей. Точные имена полей фиксируются в плане.

- **Новость** (файл на новость): заголовок, дата (календарь), текст (rich-text, Markdown), картинки.
- **Раздел «Информации»** (файл на раздел): название, порядок в меню, список пунктов.
- **Пункт раздела** (тип выбирается из трёх):
  - Статья: заголовок, текст (rich-text с картинками).
  - Документ: заголовок, PDF-файл.
  - Картинка: заголовок, одна картинка.
- **Медиа**: оригиналы в папке репозитория, оптимизированные копии создаёт сборка (~1600px, ~300 КБ).

## Screens / Flows
Редактор:
1. Вход (этап 2: приглашение по email, этап 1: аккаунт GitHub).
2. «Новости» → «Добавить» → заполнить поля → «Сохранить» → через 1–3 минуты новость на сайте.
3. «Информация» → «Добавить раздел» → ввести название → добавить пункты нужного типа → «Сохранить». Раздел появляется в меню сайта сам.
4. Правка и удаление существующего: открыть запись, изменить, «Сохранить».

Публичный сайт: одна страница-шаблон раздела вместо шести отдельных `General.jsx`, `Company.jsx` и др.; пункты раскрываются по клику, как сегодня.

Состояния ошибки: сборка упала → сайт остаётся прежним, админ репозитория получает письмо от GitHub. Редактор видит старый сайт и сообщает администратору.

## Результаты проверки Pages CMS (по документации pagescms.org)
Подтверждено:
- Коллекции файлов и одиночные файлы; поле `object` с `list: true` даёт список объектов; поле `block` даёт список объектов разной формы (подходит для трёх типов пунктов).
- Поле rich-text отдаёт Markdown или HTML, поддерживает вставку картинок через настроенную папку медиа.
- Поле image принимает несколько картинок (`multiple`, `max`), поле file принимает документы, `rename: safe` приводит имена файлов к безопасному виду.
- Редакторы приглашаются по email и обходятся без аккаунта GitHub. Они меняют контент и медиа. Конфиг `.pages.yml` и список редакторов остаются за пользователями GitHub с доступом к репо.
- Создание и удаление записей разрешается или запрещается настройкой `operations`.
- Встроенное сжатие и ресайз картинок отсутствуют. Pages CMS умеет запускать GitHub Actions по кнопке (`actions`), но сжатие выполняет наш workflow.
- Шаблоны сообщений коммитов настраиваются.

Не подтверждено:
- Русский интерфейс. Признаков локализации не найдено, задача i18n в репозитории закрыта как дубликат без видимой реализации. Исходим из английского интерфейса и компенсируем русскими подписями полей и инструкцией.
- В какую ветку пишет Pages CMS и можно ли её зафиксировать на `dev`.
- Тарифы и лимиты хостед-версии app.pagescms.org.
- Глубина вложенности списков (в документации только один уровень примеров).
- Работа поля rich-text внутри `block` внутри `list`.

Эти пункты проверяются прототипом в самом начале этапа 2 (на тестовом репозитории), до миграции.

## Alternatives Considered
1. Только GitHub web + инструкция (без CMS) — формат контента остаётся хрупким (дата в тексте, правка JS-массивов), новый раздел требует кода. Остаётся как этап 1.
2. Decap CMS — русский интерфейс из коробки, но GitHub-вход вне Netlify требует отдельного OAuth-прокси (Cloudflare Worker) и его поддержки.
3. Собственная админка `/admin` на React — максимум контроля над UX, максимум кода и поддержки, тот же OAuth-вопрос.
4. Публикация через Pull Request с одобрением разработчика — безопаснее, но противоречит цели «без участия программиста».

## Risks
- Pages CMS остаётся внешним сервисом. Данные лежат в репозитории, отказ сервиса переводит редактора на GitHub web.
- Публикация идёт без проверки человеком. Защита: проверка данных в сборке и откат через git.
- Рост репозитория от оригиналов фото (лимиты GitHub: ориентир 1 ГБ на репозиторий и на сайт Pages). Нужна оценка объёма и правило «до N МБ на файл» в инструкции.
- Миграция шести разделов и новостей требует ручной проверки каждой страницы.
- Переключение Pages с ветки `gh-pages` на источник «GitHub Actions» затрагивает прод. Нужна проверка, что файл `CNAME` и домен сохранились.

## Open Questions
- Кто и когда исправляет сертификат домена? Pages показывает `bad_authz` для HTTPS, срок действия до 2026-11-09. Это вне задачи, но срочно.
- Деплой идёт с `dev` (по умолчанию в спеке, `dev` — ветка по умолчанию) или с `main`? Gitflow с релизами сегодня заканчивается на `main`.
- Приглашается один редактор или несколько? От этого зависит схема доступа (email-приглашения Pages CMS или аккаунт GitHub).
- Нужна ли редактору возможность задавать порядок пунктов внутри раздела перетаскиванием?

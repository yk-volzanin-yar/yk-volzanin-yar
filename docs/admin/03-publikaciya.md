# 9. Публикация и проверка контента

## Публикация

Workflow `.github/workflows/deploy.yml` запускается при каждом пуше в `dev`
(в том числе из Pages CMS и веб-интерфейса GitHub) и вручную кнопкой
**Actions → Deploy → Run workflow**.

Шаги: `npm ci` → **Проверка контента** → `npm run build` → публикация в
GitHub Pages. Две публикации одновременно не идут: начатая доходит до конца,
из ожидающих запускается последняя.

`postbuild` копирует `dist/index.html` в `dist/404.html`. Поэтому прямые ссылки
вида `/info/general` открывают приложение. HTTP-код у них при этом 404, так
GitHub Pages работает с SPA.

## Проверка контента

`npm run validate-content` (скрипт `scripts/validate-content.mjs`) проверяет:

- у новости есть `title` и реальная дата `ГГГГ-ММ-ДД`;
- у раздела есть `title`, `slug` латиницей и без повторов, `order` числом;
- у пункта известный `type` и `title`; у `document` и `image` выбран файл;
- все файлы из `images`, `file`, `image` и картинки из текста есть в `public/`.

Если найдена ошибка, сборка останавливается и на сайте остаётся прошлая
версия. Ошибки видны на странице прогона в Actions с путём к файлу. GitHub
шлёт письмо автору коммита. Для правок из CMS это может быть не тот человек,
которому нужно об этом знать, поэтому падения стоит смотреть в Actions.

## Если публикация упала

1. **Actions → Deploy →** упавший прогон. Ошибки контента видны сверху страницы.
2. Исправьте файл в CMS или на github.com, сохраните. Новый прогон запустится сам.
3. Если ошибка не в контенте, перезапустите: **Re-run jobs**.

## Откат

Любую правку можно отменить через историю репозитория: найти коммит
«Изменено: … (имя)» и сделать revert или вернуть файл из прошлой версии.
